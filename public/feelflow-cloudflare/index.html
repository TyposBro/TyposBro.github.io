Moving FeelFlow from AWS to Cloudflare Workers

A plain-English guide. What we have now, what Cloudflare really is, what the move costs us, and what we recommend.

The bottom line

Short version: the move is worth doing. Rewrite the backend in TypeScript on Cloudflare Workers. Keep our Postgres database. Replace Redis with Cloudflare "Durable Objects". Keep a small Python service for the AI part.

If you read only this
  • We are overpaying while idle. Our stack costs about $185–225 per month before a single user shows up.
  • One resource is most of it. The Redis-style cache costs about $90–120 per month just to sit there.
  • The hard part is chat, not the rest. Logins, profiles, and logs are easy to move. The live chat stream is the real puzzle.
  • Redis is not a cache here — it is plumbing. We use it for locks, buffers, and history. Cloudflare's answer is one helper per user.
  • TypeScript is the right target. Cloudflare's TypeScript support is mature. The Python path is new and awkward.
  • Keep the Python AI service. That avoids the riskiest rewrite (the AI prompt logic) and keeps a hard job off Cloudflare.
  • Do not do a blind cutover. Build it all, then flip one switch — with an easy way to flip back.

What we have today

Today FeelFlow runs like a traditional business: we rent servers that stay switched on all day, even at 3am when nobody is using the app.

The stack in plain words

  • Backend: a Python web app (built with a tool called FastAPI).
  • Servers: Amazon servers that run our code all the time. This is "ECS Fargate".
  • Front door: a traffic director that sends requests to those servers. This is the "load balancer".
  • Database: the filing cabinet that stores all our data. This is Postgres (Amazon's version is called RDS).
  • Fast scratchpad: an in-memory notepad we call Redis (Amazon's version is "Valkey"). We use it for locks, live buffers, and chat history.
  • AI: the part that talks to language models. Built with tools called DSPy and LiteLLM.
  • Region: everything sits in one place — Seoul, Korea.
The cost problem

We pay for all of this around the clock. Here is the rough monthly bill when the app is doing nothing:

  • Redis/Valkey cache: about $90–120 — the biggest single line, and it is idle.
  • Network exit (NAT): about $33–43.
  • Load balancer: about $18.
  • Database: about $17.
  • Servers: about $21.

Roughly $185–225 per month that exists before any real traffic. That is the "overkill" we noticed.

Note: there are two infrastructure folders in the repo. cloud/ is the older setup. cloudnew/ is the newer cleanup (one network exit instead of two, a GitHub-based deploy, and the cache). The newer one is actually slightly more expensive because of the cache.

The big idea: a different way of thinking

Cloudflare Workers is not "cheaper servers". It is a different model of how code runs. This is the single most important thing to understand.

The one-line difference

Amazon: you pay for a shop that keeps the lights on all night, even with no customers.

Cloudflare: you pay for a market stall that appears the moment a customer walks up, then vanishes. Nothing is "on" by default.

Workers are tiny programs that run on Cloudflare's worldwide network. They wake up when a request arrives and stop when the request is done. Thousands of these run near the user, so responses feel fast everywhere.

Why this changes everything

Everything we rely on because "the server is still there" has to be re-thought. Here is the map:

  • Work done after the reply (like sending a push notification) used to just keep running. Now it must be handed to a to-do list (a "Queue") or a helper that stays alive on purpose.
  • A lock that stops two chats at once used to be a shared notepad. Now the helper itself does one thing at a time — the lock is built in.
  • The live chat buffer used to be in Redis. Now it lives in that same per-user helper.
  • Memory that stays warm (cached settings, cached AI prompts) is gone. Each request starts fresh and must rebuild what it needs.
  • Metrics dashboards need rebuilding. Cloudflare does not let us "scrape" our own app the old way.
The upside of the same idea

Idle costs disappear. No more capacity guessing. No more cache cluster to babysit. And the per-user helper gives us strong, simple correctness for chat — it removes several tricky spots in the current code.

Piece by piece: how Cloudflare handles our app

Each card shows what we do today and what it becomes. "Easy" means low risk. "Hard" means we must design it carefully.

Logins, profiles, emotion logs Easy

TodayPython web app on rented servers.
AfterTypeScript app on Workers, using a toolkit called Hono.

This is most of our endpoints. It is low risk. We keep the exact same web addresses so the phone app never notices.

Database (Postgres) Keep it

TodayPostgres on Amazon, reached over a direct connection.
AfterSame Postgres, reached through a Cloudflare connector.

We keep Postgres. Our data uses special Postgres features. Cloudflare's built-in database cannot do them. The connector pools connections and caches reads, which is a bonus.

Redis / Valkey Replaced

TodayA shared in-memory notepad.
AfterOne helper per user (a "Durable Object").

We used Redis for five jobs: locks, live stream buffer, chat history cache, a session-end result, and a cooldown timer. All five collapse into one helper per user. That also deletes a fallback table and several race bugs.

Live chat streaming Hard

TodayA background job writes tokens to Redis. The phone reconnects to read them.
AfterThe helper owns the stream and the phone tails it.
NoteThis is the highest-risk part. Build it first and test it hard.

Work after the reply Re-designed

TodayFire-and-forget jobs stay running after the response.
AfterPush a reminder to a to-do list, or hand it to the helper.

Push notifications, history writes, and memory updates split into three buckets: short safe work, guaranteed work (Queue), and stream-owned work (helper).

The AI layer Keep Python

TodayDSPy + LiteLLM inside the main backend.
AfterA small separate Python service the Worker calls.

This is a deliberate choice. Porting the AI prompt logic to TypeScript is the riskiest rewrite. Keeping Python avoids it, and keeps heavy AI work off Cloudflare's tiny workers.

Login security Easy

TodayGoogle, Apple, and Kakao sign-in, plus tokens.
AfterSame, using standard TypeScript libraries.

We keep the same secret key and the same database. That means the old and new systems trust each other's logins. That is what makes a safe switch-over possible.

Metrics and monitoring Rebuilt

TodayOur app exposes numbers that Grafana reads every 15 seconds.
AfterCloudflare pushes numbers out; Grafana reads them there.

Dashboards and alerts are work we must redo. We should set this up early, not last.

What we gain, what it costs

No migration is free. Here is the honest balance sheet.

What gets better

  • Idle cost gone. No paying for servers or a cache cluster at night.
  • Fewer moving parts. No cache cluster to run, no server capacity to guess.
  • Fewer bugs. The per-user helper removes lock races and a fallback table.
  • Faster everywhere. Code runs near the user, worldwide.
  • No data-transfer fees. Cloudflare does not charge for outbound data.

What gets harder

  • No shared memory. Every cached value must be rebuilt per request or stored.
  • Live streams bill by time. While a phone stays connected, the helper stays awake and costs money.
  • New limits to respect. Small memory, a small number of open connections, a time cap per request.
  • Different testing tools. Our Python test setup must be rebuilt for TypeScript.
  • One extra service. The Python AI service is a second thing to run and watch.
Where the money actually lands

We would delete the cache ($90–120), the network exit ($33–43), the load balancer ($18), and a server ($21). The database stays, so a small fixed cost remains. Net: likely a fraction of today's bill, with a new "per-use" cost for live streams.

What we recommend

The agreed direction is a full rewrite in TypeScript. Here is how to do it without gambling the app.

The target, in one line

TypeScript Worker (Hono) + our Postgres through the Cloudflare connector + one helper per user (replacing Redis) + a to-do list for background work + a small Python service for AI.

  1. Prove the two risky parts first. Build the per-user helper and the database connector against our real Postgres. If these work, the rest is mostly mechanical.
  2. Freeze the web contract. Keep every web address and the live-stream format byte-for-byte identical. The phone app then needs zero changes.
  3. Share the database and the login secret. Old and new systems read the same data and trust the same logins. This makes switching safe.
  4. Build in this internal order. Logins and database first, then normal features, then the live chat stream last — because chat carries all the new ideas.
  5. Switch with one lever. When everything is built, flip one routing switch. If anything is wrong, flip it back. No data is lost, because both sides share the database.
  6. Clean up after it soaks. Once the new path has run well for a while, turn off the old servers and the cache.
A caution about "big-bang"

The plan above builds everything before switching — that is the agreed style. But the switch itself should be one reversible lever, not a leap of faith.

If we flip everything live while also debugging the live-stream helper, the database connector, and the login edge cases at the same time, a bad night can take chat down for real users. Sharing the database and the login secret turns "big-bang" into "build it all, then flip a switch — and flip back if needed". That safety net is cheap. Please use it.

The five hardest jobs (and how we lower the risk)

  • 1. Live streams that survive a dropped phone. Build and test the helper before porting anything else. Lock the stream format with saved samples.
  • 2. The lock and "end of session" logic. Model it as one clear state machine inside the helper. The helper's built-in ordering removes the old races.
  • 3. Special database queries. Some reports use Postgres-only tricks. Port those as raw queries and test against a real database.
  • 4. Connection pooling rules. The connector keeps connections short. Keep our database transactions short and test under load.
  • 5. Keeping logins identical. Test each sign-in provider and the exact cookie settings. Shares the same secret and database with the old service.

Open questions for the team

These need a decision from a human. Each one has our recommendation.

  • Where does Postgres live? Keep Amazon, or move to a modern cloud database (Neon or Supabase)? We lean: move if it cuts the fixed cost — but keep Postgres either way.
  • Metrics target. Cloudflare's own analytics, or a bridge to our existing Grafana? We lean: Cloudflare + bridge.
  • Where does the Python AI service run? Cloudflare's containers, Fly.io, or a small Amazon box? We lean: Cloudflare containers, to stay on one platform.
  • Kakao web sign-in. Does our chosen library cover it, or do we build it by hand? Needs a quick check.
  • Session-end work. Run it inside the helper, or as a separate durable job? We lean: inside the helper.

Word list (plain meanings)

Every technical word used above, in one line.

Postgres
The database. A filing cabinet that stores all our data safely.
Redis / Valkey
A super-fast scratchpad kept in memory. We used it for locks, live buffers, and history.
ECS Fargate
Amazon servers that run our code all the time.
Load balancer
The front door that sends web traffic to the right server.
NAT gateway
A paid exit door that lets our servers reach the internet.
Cloudflare Workers
Tiny programs that run on Cloudflare's global network. They wake only when a request arrives.
Durable Object
A small helper that holds one user's data and does one thing at a time, in order. Like a dedicated clerk per customer.
Hyperdrive
Cloudflare's connector to a normal Postgres. It pools connections and caches reads.
D1
Cloudflare's own built-in database. We recommend not using it — it cannot do what our data needs.
Queue
A to-do list that survives crashes. Work on it is retried until it is done.
SSE (Server-Sent Events)
A one-way live stream. The server keeps pushing text updates to the phone.
CPU time
The seconds the code is actually computing — not the time spent waiting for answers.
TypeScript
A language for web code with safety checks. Cloudflare supports it well. Python is the older choice here.
Hono
A small TypeScript toolkit for building web apps on Workers.
DSPy / LiteLLM
The Python tools that talk to the AI language models.
Big-bang vs phased
Big-bang = switch everything at once. Phased = move parts over time. We build everything first, but switch with one reversible lever.
